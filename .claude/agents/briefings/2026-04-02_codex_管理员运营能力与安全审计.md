## 为什么这样做（Why）

- 用户已经明确要求后台要像成熟平台一样不仅能看统计，还要能做运营动作，所以仅保留“角色切换”已经不够。
- 我优先做的是最小成熟后台，而不是复杂 RBAC 或工单系统，因为当前平台体量更需要的是：
  - 账户可停用
  - 会话可失效
  - 密码可重置
  - 操作可审计
  - 登录风险可见
- 我没有把“停用用户”做成更复杂的 `disabled / locked / pending_review` 多状态体系，而是先收敛为 `active / suspended`，因为：
  - 当前业务规模不需要更重的状态机
  - 管理员先具备“能阻断风险用户”的能力更重要
- 审计日志和登录安全事件拆成两张独立表，而不是混在同一张表里，是为了区分：
  - 认证事件：谁在尝试登录、结果如何
  - 管理动作：管理员改了谁、做了什么

需要后续 Agent 注意：

- 当前密码重置是管理员直接设置新密码，不是邮件 / 短信找回流程。
- 当前用户状态仍是最小集，没有更细粒度的封禁策略。
- 后台已经能看安全事件，但还没有做 IP 聚合、频率限制或风控策略。
