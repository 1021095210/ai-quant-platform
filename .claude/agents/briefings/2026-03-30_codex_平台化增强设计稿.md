## 为什么这样做（Why）

当前设计原本足以支撑培训周的可演示交付，但从工程研发和平台建设角度看，还缺少五类底座能力：

- 回测结果的可复现性
- 长任务的异步编排与状态管理
- 更接近真实账单的交割单分层模型
- AI 生成与分析结果的可追溯性
- 文件上传和 AI 外发的数据治理边界

这次调整优先把这些能力写进设计和数据模型，而不是等到编码后再补，因为它们会直接影响 API 形态、表结构、环境选择和后续重构成本。

权衡：

- 没有把系统直接升级成完整生产架构，仍然保留“一周内可落地”的范围边界。
- 选择 `redis + worker` 作为最小异步方案，而不是引入更重的编排系统。
- 选择在 SQL 和文档层记录版本与快照，而不是立即设计完整审计子系统，避免超范围。
