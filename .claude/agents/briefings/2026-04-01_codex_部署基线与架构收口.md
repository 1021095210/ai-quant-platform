## 为什么这样做（Why）

- 当前代码的真实前端并不是 React/Vue，旧环境文档会误导新 Agent 和部署判断，所以必须先把技术栈说明收口到真实状态。
- 用户明确要求不仅能继续开发，还要能回答“前端、后端、数据、AI、部署、数据流、业务流”这组设计阶段核心问题，所以这些内容不能只留在对话里，必须固化到仓库文档。
- Redis 和 MinIO 已经是平台后续演进的基础设施，虽然当前主链路还没有深度依赖，但部署层必须先把它们纳入环境变量和校验脚本。
- 选择同时提供两个 compose 文件而不是把所有模式硬塞进一个文件，是为了明确区分：
  - 本地一体化部署
  - 外部托管依赖部署
- 没有把这轮工作发散成新功能开发，因为当前更关键的是让平台具备稳定接力、环境恢复和部署验证能力。

需要后续 Agent 注意：

- 这台机器没有 Docker daemon，`docker` CLI 存在但无法连到 `/var/run/docker.sock`，所以本轮没法在当前环境真实执行 `docker build` / `docker compose up`。
- 我已经验证了外部 PostgreSQL / Redis / MinIO 可连通，并用这些配置实际跑起了应用；下一位 Agent 如果进入有 Docker daemon 的环境，应优先补做容器级验证。
