## 做了什么（What）

- 将 `user_id / workspace_id` 正式接入持久化层
  - `StrategyVersionRecord` / `StrategyVersionORM`
  - `TaskRecord` / `TaskORM`
  - `TradeUploadRecord` / `TradeUploadORM`
  - `db.py` 中补了对应 sqlite migration

- 让项目、任务、上传都带真实用户归属
  - 创建策略项目时写入当前用户的 `user_id` 和 `workspace_id`
  - 创建回测、优化、复盘任务时写入当前用户归属
  - 上传交割单时写入当前用户归属

- 将私有业务 API 收口到登录态下
  - 需要登录：
    - `/api/v1/strategies/projects`
    - `/api/v1/backtests/runs`
    - `/api/v1/optimization-jobs`
    - `/api/v1/replays/analyses`
    - `/api/v1/trades/uploads`
  - 详情 / 取消 / 解析 / 记录读取也按当前用户过滤
  - 非本人资源默认按 `404 NOT_FOUND` 处理，避免跨用户泄漏

- 让工作台和列表 API 读取当前用户自己的数据
  - 项目列表
  - 回测列表
  - 任务详情

- 更新接力文档
  - 仓库内 `产品设计/AI量化交易平台_新环境恢复与Agent接力说明.md`
  - 仓库外 `/workspace/ai量化平台设计/接力文档记录/AI量化交易平台_新环境恢复与Agent接力说明.md`

- 补充测试
  - 私有接口必须登录
  - 默认用户登录后拥有 `workspace_id`
  - 项目 / 回测 / 上传按用户隔离
  - 现有回测、优化、复盘、上传链路在登录态下保持可用

## 为什么这样做（Why）

- 仅有页面登录保护是不够的，工作台和列表接口仍可能返回全局数据，所以必须把用户归属字段落到数据库并收口到查询层。
- 选择在仓储层支持 `user_id / workspace_id` 过滤，而不是只在 API 层过滤内存结果，是为了保证后续 agent 继续扩展时能复用统一边界。
- 对跨用户资源返回 `404` 而不是 `403`，是为了尽量减少资源存在性泄漏。
- 目前把公开 API 保留在“策略生成 / 指标 / 规则”这类不含个人数据的能力上，先把真正的私有资源链路收口，风险和改动范围更可控。
