# AI 量化交易平台完整测试流程与发布前步骤

## 1. 文档来源与落地原则

本流程基于以下 6 份测试方法论文档整理，并按成熟 Web 平台的发布要求收敛为当前项目的实际执行版本：

- `01_为什么AI时代需要重新理解测试.pdf`
- `02_AI代码的测试思维模型.pdf`
- `03_测试策略与分层架构.pdf`
- `04_AI辅助测试实战工作流.pdf`
- `05_持续测试与验证修复闭环.pdf`
- `07_测试用例编写实践.pdf`

落地原则：

1. 不默认信任 AI 生成代码和 AI 生成测试，测试本身也要被审核。
2. 关键业务逻辑必须至少有两层验证，不能只靠单元测试或只靠页面点点看。
3. 测试不是单次动作，而是 `发现 -> 定位 -> 修复 -> 验证 -> 回归` 的闭环。
4. 对外发布前必须同时完成代码验证、业务验证、环境验证和运营验证。
5. 覆盖率只作为辅助指标，优先保护高风险路径：认证、权限、回测可信度、数据快照、管理员操作。

## 2. 适用于本平台的分层测试架构

### 第 1 层：静态与结构门控

目标：在最便宜的阶段挡住低级错误和资源失效。

当前项目落地点：

- `tests/test_static_assets.py`
- `tools/validate_product_design_docs.py`
- `python tools/release_preflight.py`

必须覆盖：

- JS 模块语法
- 关键页面结构是否存在
- 设计文档是否仍满足基线
- 规则页、后台页、回测页等静态壳是否没有明显断裂

### 第 2 层：单元测试

目标：验证函数级逻辑、边界和执行规则。

当前项目重点对象：

- 回测引擎：成交方式、盘中撮合、T+1/T+0、仓位与风控
- 认证逻辑：登录、会话、停用用户、密码重置
- 默认规则与术语解析
- 数据快照摘要和配置归一化

执行要求：

- 新功能优先按 Spec 驱动写测试
- Bug 修复必须先补红测，再修代码
- 不能只测 happy path，必须补边界和异常路径

### 第 3 层：API / 服务集成测试

目标：验证模块协作和数据流转。

当前项目核心链路：

1. 登录 / 注册 / 会话校验
2. 策略生成 / 保存 / 读取
3. 回测创建 / 历史读取 / 对比
4. 交割单上传 / 解析 / 复盘
5. 管理员后台 / 用户状态 / 审计日志 / 安全事件

要求：

- 至少验证成功态、权限拒绝态、跨用户隔离态
- 对比类接口必须验证差异字段真实返回
- 任务类接口必须验证 `config_revision`、`dataset_snapshot_ref`、状态和值传递

### 第 4 层：浏览器与关键路径测试

目标：验证用户真实使用链路没有断。

当前平台必须覆盖的关键路径：

1. 匿名访问首页 -> 登录 -> 工作台
2. 工作台 -> 策略工坊 -> 保存策略
3. 回测中心 -> 运行新回测 -> 查看结果
4. 回测历史 -> 选择 2 条以上记录 -> 生成回测对比
5. 规则模块 -> 查看 / 编辑 / 恢复默认规则
6. 管理员登录 -> 管理后台 -> 查看用户 / 审计 / 安全事件

执行规则：

- 页面步骤必须可观察，不写“功能正常”这种空结论
- 选择器优先用可见文本和语义属性
- 动态弹层、下拉框、条件渲染必须先确认真实 DOM
- 每次外链验证都必须包含 `/healthz`

### 第 5 层：安全与运行边界

目标：防止“能用但不安全”。

当前必须检查：

- 默认测试账号在生产环境关闭
- 初始管理员通过环境变量注入
- 会话 Cookie 的 `Secure / SameSite / Domain` 配置
- 普通用户不能访问管理员接口
- 停用用户旧会话失效
- 密码重置后旧密码和旧会话失效
- 关键错误不泄露敏感信息

### 第 6 层：探索性与发布前全站检查

目标：在正式发布前补上人类没显式编写到的盲区。

适用于本平台的方式：

- 用浏览器从首页、工作台、策略工坊、回测中心、规则模块、复盘、管理员后台做一轮探索
- 重点找：
  - 死链接
  - 页面白屏
  - 规则加载失败
  - 多角色跳转错误
  - 空状态无动作

注意：

- 这层是补充层，不替代前 1-5 层
- 核心业务正确性仍以 Spec + 单测 + API 集成为主

## 3. 功能开发期的标准测试流程

### 3.1 新功能

标准顺序：

1. 先写行为规格
2. 先补失败测试
3. 实现最小代码让测试通过
4. 补边界、异常和权限测试
5. 跑相关测试
6. 跑全量测试
7. 起应用验证真实链路
8. 更新 GitHub、接力文档、简报

适用于当前平台的重点：

- 回测配置对象化
- 回测对比层
- 管理员后台能力
- 用户归属与数据隔离

### 3.2 Bug 修复

标准顺序：

1. 先复现 Bug
2. 写一条会失败的回归测试
3. 修复代码
4. 验证回归测试从红变绿
5. 跑相关模块测试
6. 跑全量回归
7. 保留该测试，永不删除

典型场景：

- 规则模块加载失败
- 角色判断错误
- 回测结果字段缺失
- 页面跳转错误

### 3.3 多模块并行改动

建议拆法：

- Agent A：正常路径
- Agent B：边界值
- Agent C：异常路径
- Agent D：安全与权限

合并前必须做：

1. 去重测试
2. 检查断言是否冲突
3. 跑集成与全量回归
4. 确认接口契约未破坏

## 4. 当前平台的对外发布前步骤

### 4.1 发布冻结

发布前先冻结以下信息：

- GitHub 提交 hash
- 版本说明
- 环境变量版本
- 管理员账号初始化方式
- 数据库迁移状态
- 回滚目标版本

### 4.2 发布前预检

必须执行：

```bash
python tools/release_preflight.py
```

该命令默认执行：

1. 设计文档校验
2. 静态资源测试
3. 发布前烟雾套件

在发布候选版本或正式发布前，还必须补跑完整回归：

```bash
python tools/release_preflight.py --full-regression
```

如需同时校验环境与健康状态：

```bash
python tools/release_preflight.py \
  --full-regression \
  --app-url https://your-app.example.com \
  --database-url postgresql://... \
  --redis-url redis://... \
  --minio-endpoint https://minio.example.com
```

预检必须至少通过：

1. 设计文档校验
2. 静态资源测试
3. 发布前烟雾套件
4. 依赖连通性与 `/healthz`
5. 正式对外发布前补跑完整回归

### 4.3 预发布环境验证

在 staging 或临时外链上完成：

1. 首页可访问
2. 登录 / 注册正常
3. 普通用户进入工作台
4. 管理员进入后台
5. 规则模块正常加载
6. 回测可创建并查看结果
7. 回测对比可读取两条以上记录
8. `/healthz` 返回环境与依赖状态

### 4.4 生产配置核查

上线前必须确认：

1. `ENABLE_DEFAULT_ACCOUNTS=false`
2. `INITIAL_ADMIN_*` 已设置
3. `SESSION_COOKIE_SECURE=true`
4. 正式域名和反向代理已配置
5. PostgreSQL / Redis / MinIO 可达
6. 日志、备份、回滚方式明确

### 4.5 上线执行顺序

建议顺序：

1. 备份数据库
2. 发布镜像 / 拉起新版本
3. 校验容器健康
4. 校验 `/healthz`
5. 管理员登录后台
6. 验证关键业务流
7. 开放用户访问

### 4.6 上线后 30 分钟观察项

重点看：

- 认证失败率
- `/healthz` 异常
- 回测创建失败率
- 规则模块加载失败
- 管理员后台错误
- Redis / PostgreSQL / MinIO 连通性

### 4.7 回滚条件

出现以下任一情况立即回滚：

1. 登录不可用
2. 回测创建或详情读取大面积失败
3. 管理员后台无法进入
4. `/healthz` 非 200
5. 关键依赖不可达且无法快速恢复

## 5. 当前平台建议采用的四级门控

### 门控 1：本地提交前

- 静态资源测试
- 本次变更相关单测
- 文档基线检查

### 门控 2：PR / GitHub

- 运行 `tools/release_preflight.py`
- AI 代码审查
- 风险评估与变更摘要

### 门控 3：准备合并主干

- 全量测试
- 关键链路浏览器验证
- 数据与配置差异复核

### 门控 4：准备部署

- 基础设施联通
- `/healthz`
- 生产配置检查
- 管理员登录与关键路径冒烟

## 6. 适用于本平台的发布标准

达到以下条件，才算“可真实给用户使用”：

1. 不是只有页面能打开，而是登录、工作台、规则模块、回测、管理员后台都可用
2. 回测结果不是只有数字，而是包含配置摘要、快照摘要、执行边界和可追溯字段
3. 角色与数据隔离生效
4. 默认测试账号不会出现在正式环境
5. 有一键预检脚本
6. 有 CI 基线
7. 有回滚条件和发布后观察项

## 7. 当前项目下一步测试建设建议

按优先级排序：

1. 给回测对比层补真实浏览器自动化测试
2. 给管理员后台补分页、筛选和操作链路测试
3. 引入 staging 发布后的冒烟脚本
4. 增加安全扫描和依赖漏洞扫描
5. 在正式部署后接入持续监控和告警
