# AI 量化交易平台周一提交版

## 1. 选题确认

### 一句话说清楚

我要做一个 `AI 量化交易研究与复盘平台`，它能帮助 `有交易经验但不会写量化代码、也缺少系统复盘能力的交易者` 解决 `策略难以快速验证、交割单复盘依赖主观经验、无法系统提升胜率` 的问题。

### 为什么选这个题

- 这是一个真实存在的高频痛点：很多交易者会交易，但不会把经验转成可验证的量化规则。
- 这个题天然适合 AI 深度参与：
  - 自然语言转策略
  - 复盘结论总结
  - 规则建议生成
- 它能完整覆盖培训要求的闭环：
  - 需求
  - 设计
  - 实现
  - 测试
  - 部署
  - 演示与复盘

### 目标用户

- 有一定交易经验的个人交易者
- 想快速验证交易想法的研究型用户
- 有历史交割单、希望用数据改进交易模式的用户

### 解决的问题

1. 用户不会写代码，无法把交易想法快速变成策略并回测。
2. 用户能看到过去赚了或亏了，但无法系统分析“为什么”。
3. 用户知道自己可能在某些场景下容易亏损，但不能把这些经验变成规则并重新验证。

## 2. 核心功能与优先级

原则：必须做的功能要构成一个最小可演示闭环。

| 功能 | 一句话描述 | 优先级 |
| --- | --- | --- |
| 自然语言生成策略 | 用户输入自然语言，平台生成结构化量化策略 | P0 |
| 内置指标与自定义指标 | 平台支持常用技术指标，也允许用户创建受限表达式形式的自定义指标 | P0 |
| 策略回测与结果展示 | 平台基于历史行情执行策略并展示收益、回撤、胜率、交易记录 | P0 |
| 交割单上传与解析 | 用户上传历史交割单，平台识别和标准化交易记录 | P0 |
| AI 复盘分析 | 平台分析盈利/亏损交易共同特征并给出优化建议 | P0 |
| 参数优化 | 平台对策略参数组合做网格搜索并输出最优组合 | P1 |
| 复盘建议回灌策略 | 将复盘建议一键转成新规则并重新回测 | P1 |
| 策略版本对比 | 比较不同版本的策略表现 | P2 |

### P0 演示闭环

如果只能演示一个闭环，我会演示：

1. 输入自然语言策略
2. 平台生成结构化策略
3. 用户补充或创建自定义指标
4. 运行回测并查看结果
5. 上传历史交割单
6. 平台输出复盘建议
7. 应用一条建议重新回测

## 3. 技术选型与理由

### 3.1 前端用什么

- 选择：`React + Next.js + TypeScript`
- 原因：
  - 适合数据工作台型产品
  - 组件生态成熟，图表和复杂表格能力强
  - 便于做“策略编辑 + 图表结果 + 复盘工作台”多区域交互

### 3.2 后端用什么

- 选择：`Python + FastAPI`
- 原因：
  - 更适合数据分析、指标计算、回测逻辑和 LLM 编排
  - 对 pandas / polars / 技术分析库的支持更自然
  - FastAPI 适合快速定义清晰 API，便于前后端分离

### 3.3 数据存哪里

- 选择：`PostgreSQL + 文件存储`
- PostgreSQL 存：
  - 用户项目
  - 策略版本
  - 回测结果元数据
  - 复盘分析结果
- 文件存储存：
  - 上传的交割单原文件
  - 行情样例文件
  - 大体量曲线或缓存结果
- 原因：
  - PostgreSQL 足够稳定，适合结构化元数据
  - 文件类数据单独存放更简单

### 3.4 有没有 AI 组件

- 选择：`LLM API + 结构化输出`
- 推荐接入方式：
  - 优先：OpenAI 兼容接口
  - 模型用途拆分：
    - 策略生成：高质量结构化输出模型
    - 复盘总结：成本更低的总结模型
- AI 用途：
  - 自然语言转策略 DSL
  - 策略解释与歧义提示
  - 复盘分析结果的人类可读总结
- 关键边界：
  - AI 不直接生成可执行交易代码
  - AI 不直接决定回测结果
  - AI 的输入必须是受控上下文，输出必须经过结构化校验

### 3.5 怎么部署

- 选择：`Docker Compose + 单机演示环境`
- 原因：
  - 一周内最稳妥
  - 能同时打包前端、后端、数据库
  - 演示时不依赖复杂云资源
- 本周默认不做：
  - 券商接入
  - 实时行情服务
  - 高可用部署

### 3.6 平台化目标与工程边界

这次设计不只把它当成一个“能演示的页面组合”，而是把它当成一个后续可继续演进的研究平台底座。

- 本周优先沉淀的平台能力：
  - 结构化策略 DSL，而不是只保存自然语言文本
  - 可复现的回测执行契约，而不是只返回一次结果
  - 长任务异步资源模型，而不是让回测和复盘长时间占用同步请求
  - 分层的交割单导入模型，而不是把原始文件直接压成单表
  - AI 输出可追溯性，而不是只保留最终摘要
- 平台化底线：
  - 同一策略版本 + 同一数据快照 + 同一执行契约，应得到同一回测结果
  - 回测、参数优化、复盘分析都必须可排队、可观察、可取消、可重试
  - AI 生成结果必须记录模型版本、提示词版本和 schema 版本
- 本周仍然不做：
  - 实盘自动交易
  - 券商下单接入
  - 高频实时行情链路
  - 生产级高可用与权限体系

## 4. 数据流转（重点）

### 4.1 策略生成与回测数据流

#### 策略生成流程

用户输入自然语言描述  
→ 前端把输入提交给后端 `generate strategy` 接口  
→ 后端构造系统提示词和结构化输出 schema  
→ 调用 LLM API  
→ LLM 返回结构化策略 DSL  
→ 后端校验 DSL 中的指标、参数、运算符是否合法  
→ 合法则保存策略版本到 PostgreSQL  
→ 返回前端展示策略规则树和解释摘要

#### 回测流程

用户点击“开始回测”  
→ 前端提交策略版本 ID、市场、周期、时间范围、手续费、滑点和执行契约  
→ 后端校验 DSL、数据范围和执行契约是否合法  
→ 后端生成回测运行记录，写入 `queued` 状态，并冻结数据快照引用、引擎版本和执行参数版本  
→ 后台 worker 读取任务  
→ 行情服务加载指定版本的 OHLCV 数据  
→ 指标引擎计算内置指标和用户自定义指标  
→ 回测引擎按统一撮合规则执行入场、出场和收益计算  
→ 生成收益指标、净值曲线、回撤曲线、交易明细  
→ 结果写入 PostgreSQL  
→ 前端通过查询接口轮询状态  
→ 回测完成后展示结果页

### 4.2 参数优化数据流

用户选择需要优化的参数范围  
→ 前端提交参数搜索空间  
→ 后端生成优化任务记录，写入 `queued` 状态  
→ 后台 worker 分批运行多组回测  
→ 聚合每组参数结果  
→ 输出最优参数、候选区间、热图数据  
→ 保存优化结果并返回前端轮询查询

### 4.3 交割单复盘数据流

用户上传交割单 CSV/XLSX  
→ 后端接收文件并校验格式  
→ 文件解析器识别列名并保存原始行数据，等待用户确认映射  
→ 用户确认字段映射后，后端先标准化为统一 fills，再聚合为完整 trade records  
→ 根据成交时间对齐历史行情数据  
→ 指标引擎在每笔交易的入场 / 持仓 / 出场时点提取特征  
→ 分析器比较盈利交易和亏损交易在量价、均线、波动率等维度上的差异  
→ 后端创建复盘分析任务并冻结特征快照版本  
→ 结构化结果传给 LLM 做解释性总结  
→ 保存结构化模式、解释摘要和建议规则  
→ 返回前端展示“成功原因、失败原因、建议规则”

### 4.4 复盘建议回灌策略数据流

用户选择一条复盘建议  
→ 前端提交建议规则和当前策略版本 ID  
→ 后端把建议转为 DSL patch  
→ 生成新的策略版本  
→ 用户重新回测  
→ 对比新旧结果

### 4.5 平台化补充：回测可信度与异步约定

- 回测可信度最小契约：
  - 明确数据快照引用
  - 明确撮合价规则
  - 明确 K 线内成交假设
  - 明确手续费、滑点、时区、交易日历、复权口径
  - 明确引擎版本和指标版本
- 长任务统一约定：
  - 回测、参数优化、复盘分析统一建模为任务资源
  - 初次请求只负责创建任务，不同步等待最终结果
  - 前端通过 `status + progress + result_ref` 查询状态
  - 平台保留取消、重试和失败诊断入口

## 5. 业务流转（重点）

### 5.1 首次使用

1. 用户打开平台首页
2. 进入策略实验室
3. 输入自然语言策略想法
4. 平台生成结构化策略
5. 用户选择内置指标或新建自定义指标
6. 用户运行回测
7. 用户看到收益、回撤、胜率、交易明细

### 5.2 日常研究使用

1. 用户打开已有策略项目
2. 调整某些参数或规则
3. 重新运行回测
4. 查看结果变化
5. 保存为新策略版本

### 5.3 交易复盘使用

1. 用户打开交易复盘页
2. 上传交割单
3. 确认字段映射
4. 选择分析维度
5. 查看盈利 / 亏损交易差异
6. 查看优化建议
7. 应用建议并重新回测

### 5.4 管理操作

1. 查看已有策略项目列表
2. 查看历史回测记录
3. 查看历史交割单解析记录
4. 查看自定义指标列表
5. 删除无用指标或旧项目

## 6. 系统模块划分

把整个系统拆成以下相对独立模块：

### 6.1 前端工作台

- 职责：
  - 页面展示
  - 策略输入与编辑
  - 图表与表格展示
  - 复盘结果可视化
- 输入：
  - 用户操作
  - 后端返回数据
- 输出：
  - API 请求
  - 页面状态和交互结果

### 6.2 API 层

- 职责：
  - 路由转发
  - 参数校验
  - 错误格式统一
- 输入：
  - HTTP 请求
- 输出：
  - JSON 响应

### 6.3 策略编排模块

- 职责：
  - 自然语言转 DSL
  - DSL 校验
  - 策略解释
  - 策略版本保存
- 输入：
  - 用户描述
  - LLM 输出
- 输出：
  - 结构化策略 DSL
  - 解释文本

### 6.4 指标引擎模块

- 职责：
  - 提供内置指标
  - 解析自定义指标表达式
  - 统一产出指标序列
- 输入：
  - OHLCV 数据
  - 指标表达式
- 输出：
  - 可供回测和复盘使用的指标值

### 6.5 回测与优化模块

- 职责：
  - 执行回测
  - 计算收益与风险指标
  - 执行参数搜索
- 输入：
  - 策略 DSL
  - 行情数据
  - 执行参数
- 输出：
  - 回测结果
  - 参数优化结果

### 6.6 交割单解析与复盘模块

- 职责：
  - 上传文件解析
  - 标准化交易记录
  - 交易特征提取
  - 盈利 / 亏损模式比较
  - AI 复盘总结
- 输入：
  - 交割单文件
  - 历史行情
  - 用户指定分析维度
- 输出：
  - 复盘摘要
  - 结构化建议规则

### 6.7 行情数据模块

- 职责：
  - 读取历史行情
  - 按市场、周期、时间范围返回标准化 K 线数据
- 输入：
  - 市场、周期、时间范围
- 输出：
  - OHLCV 数据

### 6.8 存储模块

- 职责：
  - PostgreSQL 持久化元数据
  - 文件系统或对象存储保存原始文件
- 输入：
  - 策略、回测、交割单、复盘记录
- 输出：
  - 持久化数据

### 6.9 任务编排与审计模块

- 职责：
  - 统一创建回测、优化、复盘任务
  - 管理任务状态、进度、取消、重试
  - 记录模型版本、提示词版本、数据快照版本、规则版本
  - 为问题排查提供追溯信息
- 输入：
  - API 层提交的异步任务请求
  - worker 执行状态回报
- 输出：
  - 任务状态
  - 审计记录
  - 失败原因和诊断信息

### 6.10 模块关系

前端工作台  
→ API 层  
→ 策略编排模块 / 回测与优化模块 / 交割单解析与复盘模块 / 任务编排与审计模块  
→ 指标引擎模块 + 行情数据模块  
→ 存储模块

其中：

- 策略编排模块依赖 AI 组件
- 回测与复盘都依赖指标引擎和行情数据模块
- 长任务统一通过任务编排与审计模块进入后台执行
- 存储模块为所有业务模块提供持久化能力

### 7.3 实体关系

- 一个 user 有多个 strategy_projects
- 一个 strategy_project 有多个 strategy_versions
- 一个 strategy_version 有多个 backtest_runs 和 optimization_jobs
- 一个 user 有多个 trade_uploads
- 一个 trade_uploads 有多条 trade_raw_rows
- 一个 trade_uploads 有多条 trade_fills
- 一个 trade_uploads 有多条 trade_records
- 一个 trade_uploads 可生成多次 replay_analyses

关系图可以概括为：

`用户 → 策略项目 → 策略版本 → 回测 / 优化`

`用户 → 交割单上传 → 标准化交易记录 → 复盘分析`

### 7.4 为什么这样设计

- 策略项目和策略版本分离，方便版本对比
- 自定义指标单独建表，便于复用和管理
- 回测结果和优化结果分开，避免混在一起
- 交割单上传批次和交易记录分开，方便重复解析和复盘
- 复盘分析独立存储，方便多次分析、不同维度复盘

### 7.5 存储分层

- PostgreSQL：
  - 用户、策略、版本、任务状态、回测摘要、优化摘要、交割单记录、复盘结果、审计信息
- 文件存储：
  - 原始交割单
  - 样例行情文件
  - 脱敏后的特征快照
  - 大体量缓存结果
- 运行时内存：
  - LLM 提示词
  - 临时指标序列
  - 回测中间状态

### 7.6 平台化补充：可追溯性与数据治理

- 可追溯性字段必须覆盖：
  - 策略生成：模型、提示词版本、DSL schema 版本、验证规则版本
  - 回测执行：数据快照引用、执行契约、引擎版本、任务状态
  - 复盘分析：特征快照引用、规则版本、模型和提示词版本
- 数据治理底线：
  - 原始交割单先保存原文件和原始行，再做标准化
  - 向外部 AI 发送的数据必须经过字段级脱敏
  - 上传文件需要保留期限、清理状态和删除策略

### 7.7 关键 JSON 结构

- `strategy_versions.strategy_dsl`
  - 存结构化策略规则
- `backtest_runs.metrics`
  - 存回测核心指标
- `optimization_jobs.search_space`
  - 存参数搜索范围
- `replay_analyses.suggestion_rules`
  - 存可转策略的建议规则

如果在群里汇报时被追问“为什么用了 JSONB”，回答是：

- 这是一周项目，优先支持快速迭代和结构变化

## 10. AI 在系统中的介入方式

### 10.1 策略生成

- 输入：用户自然语言策略描述、允许的 DSL schema、允许使用的指标清单
- 输出：结构化策略 DSL、解释摘要、歧义提示

### 10.2 复盘总结

- 输入：结构化复盘特征、盈利 / 亏损模式差异、用户指定分析维度
- 输出：人类可读总结、建议规则草案

### 10.3 关键限制

- AI 不做回测计算
- AI 不直接执行代码
- AI 不直接下交易指令
- AI 输出必须落入受控结构

### 10.4 AI 可追溯性

- 每次策略生成记录：
  - provider
  - model
  - prompt_template_version
  - dsl_schema_version
- 每次复盘分析记录：
  - provider
  - model
  - prompt_template_version
  - analysis_rule_version
  - feature_snapshot_ref
- 这样可以保证后续：
  - 同样输入可复现
  - 模型升级后能追踪影响
  - 导师和团队能定位 AI 给错方向的原因

## 14. 风险与应对

### 时间风险

- 风险：功能点过多
- 应对：优先保证 P0 闭环，不做实盘、不做实时行情

### 技术风险

- 风险：自定义指标如果允许任意代码会带来安全问题
- 应对：只允许白名单表达式
- 风险：回测执行规则不冻结会导致结果不可复现
- 应对：保存数据快照引用、执行契约和引擎版本

### 数据风险

- 风险：交割单格式不统一
- 应对：做字段映射确认步骤
- 风险：原始交割单直接压成单表会让复盘失真
- 应对：按原始行 → fills → 完整交易三层建模

### AI 风险

- 风险：AI 幻觉生成错误策略或错误结论
- 应对：结构化输出 + DSL 校验 + 基于事实的复盘提示

### 平台风险

- 风险：长任务全部走同步接口会导致超时、无进度、无法取消
- 应对：回测、优化、复盘统一改成异步任务资源模型
- 风险：没有数据治理边界会让上传文件和 AI 外发形成隐患
- 应对：增加脱敏、保留期限、清理状态和出站字段白名单
