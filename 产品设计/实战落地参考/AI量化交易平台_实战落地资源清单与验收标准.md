## 一、先讲清楚边界

平台不能对金融场景承诺“绝对正确、绝不出错、绝无幻觉”。

原因：

- 上游行情、财务、新闻数据会修正、延迟、断流、被限流、被反爬
- 不同数据源之间会出现口径冲突
- 历史数据与真实成交结果之间天然存在执行偏差
- 实盘撮合、部分成交、停牌、涨跌停、盘前盘后、交易所制度变化都不可能被任何静态规则永远完整覆盖
- LLM 即使接入真实数据，也可能在“总结”阶段错误推断

因此平台真正应该追求的目标是：

1. 没证据就不输出结论
2. 每个结果都能追溯来源
3. 每个回测都能复现
4. 数据冲突时拒绝给出确定答案
5. 高风险结论允许人工复核

## 二、实战落地的目标定义

只有同时满足下面四类要求，平台才接近“真实可用”：

### 1. 数据真实可追溯

- 每条行情、新闻、财务、公告、指标结果都要能回溯到原始来源
- 每次数据请求都要记录：
  - provider
  - 原始接口或原始链接
  - 请求参数
  - 请求时间
  - 返回时间
  - 时区
  - 数据快照 ID
  - 响应摘要 hash

### 2. 回测真实可复现

- 回测结果必须绑定：
  - 数据快照
  - 复权口径
  - 成交规则
  - 手续费
  - 滑点
  - 最小交易单位
  - T+1/T+0
  - 盘中撮合假设
  - 市场制度约束
- 缺少任何关键执行规则时，不允许展示成“高可信结果”

### 3. AI 回答引用化

- 金融导师、金融助手、外部信息模块必须优先返回：
  - 结论
  - 引用来源
  - 数据时间
  - 使用参数
  - 不确定项
- 没有证据时必须允许系统回答：
  - 我不知道
  - 当前数据不足
  - 数据源冲突，无法确认

### 4. 全链路可审计

- 每次研究、回测、复盘、资讯分析都要能回放：
  - 用户输入
  - 系统调用的数据源
  - 参数
  - 原始返回摘要
  - 最终展示结果
  - 模型参与步骤

## 三、必须提供的资源

下面这些资源如果没有，平台最多只能算“研究原型”，不能算“高可信实战平台”。

### 给资源提供部门的简版说明

如果你不是金融或量化人员，可以直接按下面理解：

- 我们需要的不是“一个能查数据的网站”，而是“能稳定供平台后台持续拉取的数据接口或数据文件”
- 这些数据不会让每个用户单独去请求上游，而是先进入平台自己的数据中心
- 平台会把这些数据保存、增量更新、校验后，再提供给用户页面、回测、复盘、导师、助手使用
- 所以资源提供部门要重点关注：
  - 能不能长期稳定提供
  - 能不能批量获取
  - 能不能增量更新
  - 能不能说明来源和时间
  - 能不能允许平台内部保存和使用

### A. 正式行情数据源

至少需要：

- A股正式行情源
- 美股正式行情源
- 加密货币正式行情源
- 伦敦金/贵金属正式行情源

每个市场最好提供：

- 历史日线
- 历史分钟线
- 公司行为 / 复权因子
- 停牌 / 退市 / 合约变更
- 交易日历
- 时区信息
- 最小价格变动
- 最小交易单位
- 合约乘数

没有这些，就不能保证回测口径稳定。

### B. 正式新闻/资讯源

必须尽量使用可追踪来源的新闻接口，而不是只依赖网页抓取。

每条新闻至少应带：

- 原始发布时间
- 来源媒体
- 原文链接
- 更新时间
- 唯一 ID

### C. 市场规则与制度资料

至少需要覆盖：

- A股：T+1、涨跌停、停牌、集合竞价、最小交易单位
- 美股：盘前盘后、T+0、熔断、做空限制
- 加密：7x24、现货/合约、手续费层级、资金费率
- 伦敦金：交易时段、点值、杠杆或合约规则

### D. 券商或交易接口

如果平台后续要从“研究”走向“执行”，必须有：

- 券商 API 或交易终端接口
- 沙盒环境
- 委托 / 成交 / 撤单 / 持仓真实回报

没有这层，最多只能做高可信研究平台，不能验证真实执行正确性。

### E. 正式基础设施

至少需要：

- PostgreSQL
- 对象存储（MinIO / S3）
- Redis
- 足够的磁盘与备份策略

原因：

- 数据快照要冻结
- 原始响应要归档
- 新闻与研究日志要可回放
- 回测结果要长期可复现

### F. 平台统一数据中心

必须采用：

- 平台侧统一采集
- 平台侧统一存储
- 平台侧增量更新
- 用户只读平台内部数据

不建议采用：

- 用户请求直接打第三方数据接口

原因：

- 慢
- 易限流
- 成本高
- 无法统一校验
- 无法稳定复现

## 四、强烈建议提供的资源

这些资源不是“没有就完全不能做”，但没有它们，平台很难接近机构级可靠性。

### A. 双源或三源交叉校验能力

例如：

- A股行情：主源 + 备用源
- 新闻：主源 + 原文抓取校验
- 财务数据：主源 + 交易所公告校验

作用：

- 发现源间冲突
- 降低单点错误
- 支持“冲突即拒答”

### B. 历史真值样本

至少应包括：

- 真实交割单样本
- 成交截图样本
- 回测基准策略样本
- 已知事件/新闻与市场反应样本
- 已知正确答案的导师问答样本

作用：

- 建立自动回归测试
- 建立 OCR 验收集
- 建立外部信息“正确性基线”

### C. OCR 与文档识别资源

如果复盘要支持成交截图和账单文件，最好有：

- OCR 服务或模型
- 多券商样本
- 截图模板样本
- 字段映射规则

### D. 稳定的 LLM / 推理服务

LLM 不是正确性的来源，但它决定交互质量。

至少需要：

- 稳定 API
- 工具调用能力
- 长上下文
- 可控超时与日志

## 五、建议的平台资源分层

### 1. 最低可用层

具备：

- 单源行情
- 单源新闻
- 当前数据库与对象存储
- 单一 LLM API

结果：

- 能做研究平台
- 不能声称高可信

### 2. 高可信层

具备：

- 双源行情
- 双源新闻
- 数据快照冻结
- 引用式回答
- 冲突拒答
- 回测规则显式化
- 基准样本自动回归

结果：

- 接近可实战参考

### 3. 机构级层

具备：

- 多源授权数据
- 券商/沙盒执行接口
- 人工复核流程
- 审计日志
- 监控与报警
- 备份与灾备
- 合规边界与权限体系

结果：

- 才能接近真正的投研/执行平台

## 七、验收标准

只有下面这些标准被满足，平台某一模块才能被标记为“高可信”。

### 1. 外部数据验收标准

- 所有外部数据都记录 provider
- 所有外部数据都记录抓取时间
- 所有外部数据都可绑定原始链接或原始接口标识
- 关键数据支持至少双源校验
- 数据冲突时系统会中止确定性结论输出

### 2. 回测验收标准

- 每个回测都有唯一数据快照
- 每个回测都记录执行规则
- 每个回测都记录市场制度假设
- 回测结果可以重跑得到同一结果
- 未实现的执行约束会被明确显示为限制，而不是被忽略

### 3. AI 回答验收标准

- 回答中出现结论时必须有引用依据
- 回答中必须标记数据时间
- 回答中必须标记不确定项
- 无证据时允许拒答
- 数据源冲突时允许拒答

### 4. 复盘验收标准

- OCR 识别结果必须进入人工确认流
- 文字识别生成的买卖规则必须能展示推导过程
- 识别得到的价格必须标明来源
- 自动补全盈亏时必须可追溯到行情快照

### 5. 运维验收标准

- 有健康检查
- 有应用日志
- 有用户报错日志
- 有数据源调用日志
- 有对象存储与数据库备份策略

## 十、当前默认工作规则

从本文件建立之后开始，后续涉及“结果真实性、回测可信度、外部信息正确性”的开发，都默认遵循：

1. 不再把“正确性要求”只停留在口头要求
2. 新资源一旦提供，就必须落记录到本文件
3. 新 Agent 如果要改导师、助手、外部信息、回测可信度，必须先看本文件
4. 平台以后必须逐步从“能回答”升级到“有证据才回答”
