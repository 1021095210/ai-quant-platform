# AI量化交易平台资源源选型建议

> 更新时间：2026-04-07 UTC  
> 目标：给“实战落地资源清单与验收标准”里的所有关键资源提供简明选型建议。  
> 原则：没有单一源能保证绝对正确。正式方案必须采用“主源 + 备用源 + 官方回查 + 证据链”。

---

## 一、直接结论

### 数据调用方式

- 不让用户请求直接打上游接口
- 所有上游源只供平台后台任务使用
- 用户只读平台内部数据中心
- 平台内部做增量更新、快照冻结、双源校验

### 现在最值得落地的高性价比方案

- A股行情：`Tushare Pro` 主源 + `AkShare` 备用 + `上交所/深交所/巨潮资讯` 回查
- 美股行情：`Alpaca` 主源 + `SEC EDGAR` 公告/财务真值 + `FRED/ALFRED` 宏观
- 加密行情：`Binance 官方 API` 主源 + 第二交易所官方 API 备用
- 新闻资讯：`官方公告源` 优先 + `NewsAPI` 这类聚合器补充，不把聚合器当真值源
- 市场规则资料：优先 `交易所 / 监管 / 官方规则文件`
- 历史真值样本：优先内部真实样本库，其次脱敏历史样本
- OCR：先用 `OCR 服务 + 人工确认流`
- 券商/执行：先接 `沙盒/纸面交易接口`
- 基础设施：`PostgreSQL + MinIO + Redis`
- 统一数据层：自建平台数据网关，参考 `OpenBB` 的 provider 结构
- LLM：保留 OpenAI 兼容链路，但必须做引用式回答，不把 LLM 当真值源

### 如果要更高可信

- A股主源升级到：`Wind` 或 `iFinD / Choice`
- 美股主源升级到：`Polygon`
- 新闻升级到：企业级财经新闻源 + 官方公告回查

---

## 二、按资源类别给建议

## 1. A股行情与基本面

### 推荐顺序

1. `Wind`
2. `同花顺 iFinD`
3. `Choice`
4. `Tushare Pro`
5. `AkShare`

### 建议定位

- `Wind / iFinD / Choice`：正式高可信主源
- `Tushare Pro`：高性价比主源 / 正式备用源
- `AkShare`：开发辅助源 / 备用源

### 官方回查必接

- 上交所
- 深交所
- 巨潮资讯

### 我当前建议

- 现在：`Tushare Pro + AkShare + 交易所公告回查`
- 后面预算允许：升级 `Wind` 优先

---

## 2. 美股行情、财务与公告

### 推荐顺序

1. `Polygon`
2. `Alpaca`
3. `SEC EDGAR`
4. `FRED / ALFRED`

### 建议定位

- `Polygon`：正式高质量行情主源
- `Alpaca`：高性价比开发/研究/纸面交易主源
- `SEC EDGAR`：公告/财务真值源，必接
- `FRED / ALFRED`：宏观真值源，必接

### 我当前建议

- 现在：`Alpaca + SEC EDGAR + FRED`
- 后面升级：`Polygon + SEC EDGAR + FRED`

---

## 3. 加密货币行情

### 推荐顺序

1. `Binance 官方 API`
2. 第二家主流交易所官方 API

### 建议定位

- 交易所官方 API：主源和备用源
- 第三方聚合服务：可做补充，不建议做唯一真值源

### 我当前建议

- 现在：`Binance 官方 API`
- 后面：补第二交易所做交叉校验

---

## 4. 新闻、资讯与外部信息

### 推荐顺序

1. `官方公告 / 监管披露 / 交易所公告`
2. `企业级财经新闻源`
3. `NewsAPI` 这类聚合器

### 建议定位

- 官方公告源：事实真值层
- 企业级财经新闻源：正式新闻主源
- 聚合器：线索发现层，不是最终真值层

### 我当前建议

- 现在：`官方公告优先 + 聚合新闻补充`
- 后面：预算允许再接企业级财经新闻源

---

## 5. OCR / 交割单识别

### 推荐顺序

1. `商业 OCR 服务`
2. `自建 OCR 模型`

### 建议定位

- 商业 OCR：先上线最稳
- 自建模型：后续在有样本库后再做

### 必要条件

- 多券商样本
- 截图样本
- 人工确认流

### 我当前建议

- 先接商用 OCR
- 所有 OCR 结果都必须人工确认后入库

---

## 6. 市场规则与制度资料

### 推荐顺序

1. `交易所官方规则文件`
2. `监管机构正式文件`
3. `券商规则说明`

### 建议定位

- 交易所/监管：事实规则源
- 券商说明：执行补充源

### 我当前建议

- A股优先收集：T+1、涨跌停、停牌、集合竞价、最小交易单位
- 美股优先收集：盘前盘后、T+0、熔断、做空限制
- 加密优先收集：现货/合约规则、手续费层级、资金费率

---

## 7. 历史真值样本

### 推荐顺序

1. `内部真实样本`
2. `脱敏样本库`

### 建议定位

- 真实样本：回测/OCR/导师正确性基线
- 脱敏样本：开发与测试补充

### 我当前建议

- 至少准备：
  - 真实交割单样本
  - 成交截图样本
  - 回测基准样本
  - 已知事件与市场反应样本
  - 已知正确答案的导师问答样本

---

## 8. 券商 / 执行接口

### 推荐顺序

1. `券商沙盒 / 纸面交易接口`
2. `正式交易接口`

### 建议定位

- 沙盒：先验证执行链路
- 正式接口：后续再接，不建议一开始直接上

### 我当前建议

- 先接可用沙盒
- 先做“研究 -> 模拟执行 -> 对账验证”

---

## 9. 基础设施

### 必选

- `PostgreSQL`
- `MinIO / S3`
- `Redis`

### 可选增强

- 独立日志系统
- 监控与报警
- 备份和归档

### 我当前建议

- 现阶段继续用你已提供的 `PostgreSQL + Redis + MinIO`

---

## 10. 统一数据接入层

### 推荐顺序

1. `自建统一数据网关`
2. `参考 OpenBB provider 架构`

### 必须做到

- provider 标记
- 请求参数记录
- 数据快照 ID
- 响应摘要 hash
- 双源冲突标记

### 我当前建议

- 不直接把数据源裸接到导师/助手
- 先做统一数据证据层

---

## 11. LLM / 推理服务

### 推荐顺序

1. `稳定的 OpenAI 兼容 API`
2. `支持工具调用和长上下文的模型`

### 建议定位

- LLM 负责总结、解释、编排
- 不负责真值判定

### 必须做到

- 有引用才回答
- 无证据可拒答
- 冲突数据可拒答

### 我当前建议

- 保留现有 LLM 链路
- 下一阶段重点不是换模型，而是加证据约束

---

## 三、按预算给你的最优建议

### 方案 A：最低成本可用

- A股：`Tushare Pro + AkShare + 交易所公告回查`
- 美股：`Alpaca + SEC EDGAR + FRED`
- 加密：`Binance 官方 API`
- 新闻：`官方公告 + NewsAPI 补充`
- 规则资料：`交易所 / 监管官方文件`
- 真值样本：`内部真实样本 + 脱敏样本`
- OCR：商用 OCR
- 执行：沙盒接口

### 方案 B：高可信平衡版

- A股：`Wind / iFinD / Choice` 主源 + `Tushare Pro` 备用
- 美股：`Polygon` 主源 + `Alpaca` 补充 + `SEC EDGAR`
- 加密：`Binance + 第二交易所官方 API`
- 新闻：企业级财经新闻源 + 官方公告回查
- 规则资料：官方规则文件全量归档
- 真值样本：覆盖回测、OCR、问答、复盘
- OCR：商用 OCR + 样本库
- 执行：沙盒 + 正式接口预留

### 方案 C：机构级正式版

- A股：`Wind` 主源 + `iFinD / Choice` 备用
- 美股：高等级专业行情服务 + `SEC EDGAR`
- 加密：多交易所官方 API
- 新闻：企业级财经新闻授权源 + 官方公告链
- 规则资料：按市场建立正式规则库
- 真值样本：长期维护机构级样本库
- OCR：商用 OCR + 自建优化
- 执行：正式券商接口 + 审计对账

## 四、我的最终推荐

### 现在就定的第一阶段

- A股：`Tushare Pro + AkShare + 交易所公告回查`
- 美股：`Alpaca + SEC EDGAR + FRED`
- 加密：`Binance 官方 API`
- 新闻：`官方公告优先 + 聚合新闻补充`
- OCR：商用 OCR
- 执行：沙盒接口
- 基础设施：继续用现有 `PostgreSQL + Redis + MinIO`

### 第二阶段升级

1. A股主源升级到 `Wind`
2. 美股主源升级到 `Polygon`
3. 新闻升级到企业级财经新闻源
4. 建立双源冲突校验

---

## 五、不建议现在这样做

- 不要把 `AkShare` 当唯一正式真值源
- 不要把普通新闻聚合器当最终事实源
- 不要让 LLM 直接充当真假判断器
- 不要在没有双源校验前宣传“绝对正确”
