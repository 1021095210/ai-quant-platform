# 策略工坊模块详细查缺补漏

> 目标：把“自然语言转量化策略”从当前可演示状态，推进到真正能满足真实用户任务、且尽量避免误解、编造和错误执行的状态。

## 一、模块核心用户任务

策略工坊真正要完成的不是“生成一段 Python 代码”，而是帮助不同层级用户完成下面 4 件事：

1. 把口语化、非技术化的交易想法准确整理成结构化策略。
2. 在生成前就明确平台当前是否真的支持该市场、周期和执行方式。
3. 把模糊表达、冲突条件、缺失参数显式暴露出来，让用户补充或确认。
4. 在确认理解正确之后，再生成可保存、可回测、可继续迭代的策略版本。

## 二、当前已完成能力

- 支持自然语言输入并生成基础 `strategy_dsl` 和 `strategy_python`
- 支持多市场语义：
  - A股
  - 美股
  - 加密货币
  - 伦敦金
- 支持混合周期语义：
  - `1m / 5m / 15m / 30m / 1h / 4h / 1d / 1w / 1mo`
- 支持能力声明与市场支持状态矩阵
- 支持策略名称、版本标签、保存项目、版本管理
- 支持教学模式、术语库、自定义指标库预览
- 已有回测边界提示：
  - A股日线可真实回测
  - A股混合周期 / 非日线仅日线兼容层
  - 其他市场当前仅语义层

## 三、当前主要缺口

### 1. 还没有“结构化理解确认卡”

当前用户点“生成 Python 策略”后，会直接看到：
- Python 策略代码
- 规则规格
- 歧义提示

但还没有一个独立、清晰、面向用户确认的“系统理解结果”层。缺少这一层会导致：
- 用户不知道系统到底把哪句话理解成了哪条规则
- 用户只能被动看最终 DSL / Python，而不是先确认理解是否正确

### 2. 还没有“需补充信息 / 澄清提问”链路

当前如果用户写：
- “量能明显放大”
- “大盘不差时才做”
- “不要追高”
- “确认后再进”

系统还没有一个正式机制把这些模糊表达转成：
- 待确认项
- 待补参数
- 待选择定义

这会让平台容易出现两种风险：
- AI / 规则擅自补全，导致误解
- 生成了代码，但用户并不真的认可其含义

### 3. 还没有“结构化策略规格层”完整显式展示

当前虽然已经有 `strategy_dsl`，但它更像“内部结果输出”，还不是一张面向用户的结构化确认视图。后续真实可用的真值层应明确拆成：

- 市场
- 时间周期
- 数据依赖
- 条件树
- 入场条件
- 出场条件
- 风控条件
- 仓位条件
- 执行假设
- 不确定项
- 平台支持状态

### 4. 风险与支持范围校验仍不够系统化

当前已经有能力声明和部分歧义提示，但仍缺一张真正的硬校验清单。至少还需要系统化检查：

- 当前市场是否支持真实回测
- 当前周期是否支持真实执行
- 是否混合周期
- 是否涉及平台暂不支持的数据依赖
- 是否存在未来函数风险
- 是否缺必要参数
- 是否引用了平台不存在的指标
- 是否有逻辑冲突
- 是否存在“语义可描述，但执行不可落地”的情况

### 5. 生成结果还偏“先代码后确认”

当前页面主视觉仍然是：
- 左边输入
- 右边 Python 代码

这更像“代码生成器”，不够像“策略理解与确认台”。对真实用户来说，更合理的顺序应该是：

1. 输入策略想法
2. 查看系统理解结果
3. 补充不确定项
4. 确认支持边界
5. 再生成 DSL / Python

### 6. 还没有“拒绝输出 / 降级输出”机制说明

如果用户输入的策略：
- 平台当前不支持
- 风险过高
- 明显模糊
- 依赖数据不存在

系统目前缺少明确产品规则来区分：
- 可直接生成
- 可描述但不可执行
- 需补充后再生成
- 应拒绝输出

## 四、该模块中 AI 应进入的具体环节

### 1. 用户意图理解层

AI 必须负责：
- 理解自然语言策略意图
- 识别市场、周期、指标、入场、出场、风控、仓位、执行假设
- 识别跨周期逻辑和条件依赖

### 2. 术语标准化层

AI 可以参与，但必须结合平台字典：
- 技术指标术语
- 平台术语库
- 自定义指标库
- 行情与市场表达映射

### 3. 澄清候选生成层

AI 应负责把模糊表达整理成待确认问题，例如：
- “量能放大”需要补充阈值
- “不追高”需要补充价格约束
- “确认后入场”需要补充确认条件

### 4. 教学解释层

AI 可负责：
- 解释系统理解
- 用更通俗语言解释 DSL
- 给新手说明策略含义和风险

## 五、不能交给 AI 的环节

下面这些必须由平台自己的结构和规则硬约束：

### 1. 真值层定义

平台自己的结构化策略规格才是真值层，不能让 AI 自由定义字段。

### 2. 支持范围判断

例如：
- 当前市场能不能真实回测
- 当前周期能不能真实执行
- 当前数据链路是否存在

最终判断必须由平台规则决定。

### 3. 未来函数风险判断

AI 可以提示，但最终是否构成未来函数，必须由平台硬规则判断。

### 4. 条件合法性和冲突检查

例如：
- 条件缺参数
- 条件互相冲突
- 指标不存在
- 仓位 / 执行假设不一致

### 5. DSL / Python 生成边界

不能直接“自然语言 -> Python”。必须是：

自然语言  
-> AI 理解  
-> 结构化策略规格  
-> 平台校验  
-> 用户确认  
-> DSL / Python

## 六、结构化策略规格层建议字段

策略工坊下一步应把真值层显式化成下面这套结构：

- `market_scope`
- `asset_type`
- `market`
- `primary_timeframe`
- `timeframes`
- `analysis_mode`
- `data_dependencies`
- `entry_conditions`
- `entry_context`
- `exit_conditions`
- `exit_context`
- `risk_controls`
- `position_rules`
- `execution_assumptions`
- `unsupported_items`
- `ambiguities`
- `questions_for_user`
- `capability_summary`

其中：
- `ambiguities` 表示系统已识别但含糊的部分
- `questions_for_user` 表示必须补充后才能进入更可靠生成
- `unsupported_items` 表示当前平台不支持的部分

## 七、建议的用户交互流程

### 第一步：输入自然语言策略

用户描述策略想法。

### 第二步：系统输出“结构化理解确认卡”

至少展示：
- 市场
- 主周期
- 观察周期
- 入场条件
- 出场条件
- 风控条件
- 仓位条件
- 执行假设

### 第三步：展示澄清项与风险项

系统明确标出：
- 待补参数
- 模糊条件
- 不支持条件
- 未来函数风险
- 支持边界

### 第四步：用户确认或补充

用户可：
- 直接确认
- 修改条件
- 回答待补问题
- 放弃生成

### 第五步：生成 DSL / Python / 保存版本

只有在理解结果明确后，才进入最终生成与保存。

## 八、需要补的错误态与拒绝输出场景

后续实现时必须支持下面这些明确状态：

### 1. 可直接生成

表达清晰、字段完整、平台支持。

### 2. 可描述但不可真实执行

例如：
- 非 A股市场
- 混合周期但当前只有兼容层

这时允许保存语义，但必须明确不可真实执行。

### 3. 需补充后再生成

例如：
- “量能放大”
- “不要追高”
- “大盘不差时”

这类表达不应直接生成最终策略。

### 4. 应拒绝输出

例如：
- 依赖平台完全没有的数据
- 明显未来函数
- 条件严重冲突
- 关键字段缺失且无法合理推断

## 九、该模块还需要的资源

如果要把策略工坊真正做成“自然语言 -> 量化策略”可靠主链路，还缺这些资源：

- 稳定的结构化 JSON LLM 接口
- 更多真实用户策略表达样本
- 平台支持指标与条件的标准字典
- 多市场执行规则与数据依赖映射
- 未来函数风险规则库
- 混合周期执行边界规则库

## 十、验收标准

策略工坊下一阶段不应只验“能不能生成代码”，而应按下面标准验收：

### 1. 理解正确性

- 用户能明确看到系统理解结果
- 复杂策略表达不会直接跳过确认
- 模糊条件会进入待确认而不是被悄悄补全

### 2. 边界正确性

- 市场支持、周期支持、回测支持必须明确
- 平台不支持的内容不会伪装成支持

### 3. 风险正确性

- 未来函数风险会被提示
- 条件冲突会被提示
- 缺参数会被提示

### 4. 结果可用性

- 生成的 DSL 可读、可保存、可继续编辑
- 生成的 Python 是结构化规格的派生物，而不是独立黑盒

## 十一、下一步研发优先级

### P0

- 增加“结构化理解确认卡”
- 增加“待补充问题 / 待确认项”机制
- 增加“可直接生成 / 需补充 / 可描述不可执行 / 拒绝输出”状态体系

### P1

- 增加“自然语言 -> 结构化规格 -> DSL/Python”并排视图
- 增加更系统的风险与支持范围校验清单
- 把术语库和指标库真正接进理解确认卡

### P2

- 接入更强的 LLM 结构化理解链路
- 支持更复杂的多周期、多市场和执行假设表达
- 补更完整的教学解释层

## 十二、与交易复盘模块的关系

策略工坊和交易复盘与优化后续应形成真正闭环：

- 策略工坊负责把“想法”准确结构化
- 回测中心负责把“规则”真实验证
- 交易复盘与优化负责把“真实成交”反推成可优化规则
- 复盘建议后续应能回灌到策略工坊的结构化规格层，而不是只给一段文字建议

因此策略工坊下一步实现时，必须优先考虑和：
- 回测中心
- 交易复盘与优化
- 指标设置
- 规则模块

的结构兼容性。
