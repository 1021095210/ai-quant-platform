# AI量化交易平台评审：应用平台设计视角（2026-04-01）

本文以“挑剔的成熟 Web 应用平台设计专家”的标准评审当前版本（以仓库 `/workspace/ai-quant-platform` 为准）。不涉及代码改动，仅给出按优先级排序、可落地的改进建议。

## P0（必须修，否则会误导用户/导致扩展成本指数上升）

- **产品能力与真实可执行能力的边界需要更明确地呈现**
  - 问题: 多市场、混合周期 DSL 在策略/规则层已出现，但真实回测执行仍以兼容层为主。首页已收敛为入口页，但整体站内仍缺少“能力边界”的统一表达。
  - 风险: 用户误以为“多市场可回测可复盘已打通”，产生信任落差；后续扩展时文案与交互会反复返工。
  - 建议方案: 将“能力矩阵”移动到登录后的工作台或帮助页（非首页），用统一组件表达:
    - `可描述 / 可保存 / 可回测 / 可复盘 / 可执行` 五档能力
    - 按市场与周期列出覆盖状态，并在回测结果页强制展示本次使用的执行假设

- **鉴权与权限边界需要做成可验证的“平台契约”，而不是页面跳转约定**
  - 问题: 当前通过“未登录跳转登录页”保护页面是对的，但仍需确保 API 端点权限与资源归属一致、错误语义一致。
  - 风险: 前端跳转容易被绕过；后续接入更多客户端/服务时容易出现越权读取。
  - 建议方案:
    - 统一在后端对资源做 `user_id/workspace_id` 校验并返回一致的错误 envelope（已部分实现，建议补齐清单）
    - 对每个私有资源列出“归属字段、查询条件、越权返回语义(404/403)”并写入接力文档

- **命名与信息架构需要收敛成“用户任务模型”**
  - 问题: 目前模块较多（策略/指标/规则/回测/复盘），用户在工作台缺少“我现在应该做什么”的线索，模块更像平铺入口。
  - 风险: 新用户无法形成心智模型，留存会差；后续功能增加会让导航失控。
  - 建议方案: 以“研究项目/实验/回测运行/复盘记录”作为顶层对象重排工作台:
    - 工作台默认视图为“最近项目 + 最近实验 + 最近任务 + 待办”
    - 模块页更多作为“工具页”，而不是主导航入口

## P1（强烈建议，提升成熟度与效率）

- **空状态、加载态、错误态需要成体系**
  - 问题: 多页面仍偏“空容器+一句话”。错误提示与后续动作不足。
  - 风险: 用户卡住不知道下一步；真实环境下问题排查困难。
  - 建议方案:
    - 每个列表页定义 `empty/loading/error` 三态组件
    - 错误提示带 `request_id` 与可操作建议（重试/去规则页补齐/去工作台检查任务）

- **表单体验（登录/注册/策略输入）需要更符合成熟平台**
  - 问题: 表单校验、密码强度提示、错误定位、回车提交、禁用重复提交等细节若缺失，会显得“demo 感”重。
  - 风险: 注册转化下降；登录失败无法自助排查。
  - 建议方案:
    - 表单校验前置（用户名格式、手机/邮箱格式、密码规则）
    - 提交中态与防重复提交
    - 登录失败提供明确错误码与用户可理解的说明（不泄露敏感信息）

- **文案与语气需要“运营级一致性”**
  - 问题: 中英混用（如 `Platform Home`、`Step 1`），以及部分叙述偏“开发说明书”。
  - 风险: 平台可信度下降。
  - 建议方案: 建立 `文案规范` 小节（术语表、语气、避免暴露实现细节），逐页替换中英混用与开发口吻。

## P2（可后置，但做了会明显更专业）

- **视觉系统再收敛一轮（token 化）**
  - 问题: 局部仍有 inline style 与组件权重接近，层级不够清晰。
  - 风险: 迭代越多越难保持一致。
  - 建议方案:
    - 将常用间距、卡片、网格、标签、按钮状态抽成 CSS 变量/utility
    - 减少 inline style，统一通过类名控制布局

- **可观测性与可排障能力**
  - 建议方案:
    - 前端记录关键行为与失败原因（不含敏感数据），后端对任务链路提供 trace_id 贯通
    - 工作台提供“最近错误”面板，直达对应任务与 request_id

## 实现风险提示（给后续开发的红线）

- 多市场与混合周期在语义层扩展很快，但执行层落地要优先解决: 交易日历/时区/数据对齐/未来函数检测/成交假设可配置，否则越做越难兜底。
- 如果继续增加模块页入口而不收敛顶层对象（项目/实验/任务），信息架构会在两周内失控。
