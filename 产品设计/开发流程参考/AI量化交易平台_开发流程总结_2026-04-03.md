# AI量化交易平台开发流程总结

> 日期：2026-04-03  
> 用途：这不是给新 Agent 恢复环境用的接力文档，而是基于本次完整开发过程沉淀出的“开发流程参考”。  
> 目标：让下一次继续开发时，能更快按正确顺序推进，减少返工、遗漏和重复提醒。

---

## 一、这份文件解决什么问题

这份文件主要解决三类问题：

1. 下一次继续开发时，应该先做什么、后做什么，避免顺序错乱  
2. 每轮开发结束时，哪些动作必须一起完成，避免“代码改了但流程没收口”  
3. 这次开发里反复出现过哪些问题，后续怎么主动规避

这份文件不替代主接力文档。

- 主接力文档负责：新环境恢复、GitHub 仓库接手、当前项目基线、模块索引
- 本文件负责：开发推进方法、节奏、检查项、收尾规则

---

## 二、推荐的标准开发顺序

以后继续开发时，优先按下面顺序推进，而不是想到哪里改哪里。

### 1. 先确认当前任务属于哪个模块

先判断任务落在哪个模块：

- 首页
- 用户工作台
- 管理员工作台
- 认证与账户
- 策略工坊
- 指标设置
- 规则模块
- 回测中心
- 交易复盘
- 金融导师
- 金融助手
- 平台基础设施与部署

如果任务跨多个模块，先明确主模块，再列出受影响的次级模块。

### 2. 先读当前模块文档，再看代码

推荐顺序：

1. 先读主接力文档  
2. 再读对应模块文档  
3. 如果是重复故障或用户多次指出的问题，再读常见问题文件  
4. 最后才进入代码与页面修改

这样可以减少“已经有设计决策但又重复试错”的情况。

### 3. 先修真实链路，再做外围优化

如果一个问题同时涉及：

- 页面文案
- 交互细节
- 后端逻辑
- 数据结构

优先顺序应该是：

1. 先保证真实链路可用  
2. 再保证结果正确  
3. 再优化解释、交互和视觉层次

不要一开始只改界面表达，而底层逻辑仍然不能用。

## 三、一次标准开发回合应该怎么走

建议固定为下面 8 步。

### 第 1 步：明确任务边界

- 任务目标是什么
- 属于哪个模块
- 会影响哪些文件
- 是新功能、问题修复、设计优化，还是流程治理

### 第 2 步：查看当前基线

- 查看主接力文档
- 查看对应模块文档
- 查看最近 2 到 3 份简报
- 查看 `ACTIVE_TASKS.md`

### 第 3 步：登记当前任务

在 `ACTIVE_TASKS.md` 里写明：

- 任务是什么
- 涉及哪些文件 / 模块
- 开始时间

这样做的意义不是形式，而是避免多 agent 冲突。

### 第 4 步：先做最小可用改动

不要先大范围扩展。

推荐方法：

- 先做能闭环的最小实现
- 再补边界情况
- 再补 UI / 交互 / 文案优化

这次开发里很多有效推进，都是先把主链路打通，再逐步精修。

### 第 5 步：补测试

每次改动后都要补测试，至少覆盖下面之一：

- 后端接口测试
- 页面静态资源测试
- 新文档 / 工件存在性测试
- 核心流程回归测试

如果改动是前端脚本，还要特别检查：

- 是否有语法错误
- 是否有缓存版本号
- 是否真的在浏览器里能运行

### 第 6 步：做真实验证

不要只看测试通过。

每轮至少做一种真实验证：

- 本地浏览器打开页面
- 调接口看真实返回
- 登录后走一遍用户链路
- 外部链接访问验证

这一步非常关键，因为本次开发里多次出现过：

- 测试没报错，但真实页面卡住
- 后端接口正常，但前端脚本因缓存或语法问题无法显示

### 第 7 步：同步文档和说明

每轮开发完成后，至少同步：

- 主接力文档
- 对应模块文档
- 必要时更新常见问题文件
- 本轮工作简报

注意：

- 周报、汇报、阶段复盘，不需要写进主接力文档说明
- 主接力文档仍然只服务于“发给新 Agent 后就能继续开发”

### 第 8 步：提交、推送、清理登记

结束前统一做：

1. 跑测试  
2. 提交本轮修改  
3. 推送到 GitHub  
4. 清理 `ACTIVE_TASKS.md`  
5. 给用户发可访问链接和结果摘要

## 四、这次开发中验证有效的工作方法

下面这些方法，在这次完整开发流程里是验证过有效的。

### 1. 先恢复环境，再继续开发

不要跳过：

- 仓库恢复
- 环境搭建
- 测试验证
- 服务启动
- 页面检查

如果这一步没做扎实，后续功能开发会一直建立在不稳定基线上。

### 2. 设计冻结稿先落代码，再做页面包装

本次推进里最稳的一条路径是：

1. 先把平台契约、数据边界、任务模型落地  
2. 再把用户归属和权限模型落地  
3. 再把页面和交互逐步做深

这样能避免 UI 很完整，但数据和接口还停留在演示级。

### 3. 复杂页面要用“完成一步点亮下一步”的交互

这次证明有效的做法包括：

- 策略生成成功后，再点亮“保存项目 / 去回测中心”
- 指标生成成功后，再点亮“保存到自定义指标库”
- 交易复盘先导入 / 解析成功，再点亮“运行 AI 复盘”

对于非专业用户，这种引导很重要。

### 4. 面向真实用户时，术语必须解释清楚

不能直接把内部字段露给用户，例如：

- `t_plus_one`
- `raw`
- `qfq`
- `undefined`

这些都应该翻译成用户可理解的中文解释，并在必要时加提示说明。

### 5. 新模块最好先做“第一阶段可用版”

例如：

- 金融导师：先做解释与追问，再接真实 LLM
- 金融助手：先做工作流 + 专家编组 + 结构化输出第一阶段
- OCR：先做识别后人工确认，而不是一步到位自动入库

这种做法比一开始追求“大而全”更稳。

## 五、以后继续开发时的固定检查清单

每轮开发结束前，建议按下面清单过一遍。

### 功能层

- 真实主链路是否可用
- 是否有明显空状态 / 错误状态没处理
- 是否有用户看不懂的术语直接暴露
- 是否存在“应该禁用却还能点”的按钮

### 技术层

- 测试是否新增或更新
- 静态资源是否做了真实检查
- 是否有旧数据库兼容问题
- 是否误改了运行态数据库文件

### 流程层

- 是否更新了接力文档
- 是否更新了对应模块文档
- 是否更新了简报
- 是否清理了 `ACTIVE_TASKS.md`
- 是否同步到了 GitHub

### 对用户交付层

- 是否给了可访问链接
- 链接发出前是否真的验证过可打开
- 是否说明了已知限制和下一步建议

## 六、本次开发里最容易重复犯错的地方

### 1. 只看测试，不看真实页面

这是最容易重复犯的问题。

正确做法：

- 改完前端页面或脚本后，一定要真实打开页面
- 必要时用浏览器自动化截图验证

### 2. 临时外链发出去之前没有再次确认

临时隧道会失效，必须先验证再发。

正确做法：

1. 先确认本地服务正常  
2. 再确认隧道正常  
3. 再用 `healthz` 和首页做一次真实访问验证  
4. 最后再把链接给用户

### 3. 主接力文档塞进太多非接力内容

以后要继续控制边界：

- 主接力文档：只做恢复与继续开发入口
- 周报 / 汇报 / 复盘：单独放别的目录
- 模块状态：放模块文档

### 4. 把面向新手的平台写成只给老交易员看的工具

这次用户反复强调的平台定位是：

- 面向有经验交易员
- 也面向没有量化经验的新手
- 甚至面向刚接触交易的股民

所以后续继续开发时必须同时兼顾：

- 专业能力
- 易理解性
- 操作引导

---

## 七、建议以后沿用的发布节奏

以后比较稳的节奏是：

1. 先做一个模块或一条主链路  
2. 立刻补测试  
3. 立刻做真实页面或接口验证  
4. 立刻同步文档和 GitHub  
5. 再进入下一个模块

不要把很多功能堆积到最后一起验证，否则问题会很难回溯。

---

## 八、下次继续开发时的建议起手式

如果下一次要继续开发，建议按这个顺序起手：

1. 先把 `AI量化交易平台_新环境恢复与Agent接力说明.md` 发给新 Agent  
2. 让它恢复项目并确认当前平台可运行  
3. 让它根据当前要改的模块去读对应模块文档  
4. 如果任务涉及用户重复反馈，再让它读常见问题文件  
5. 最后按本文件的“标准开发顺序”和“固定检查清单”推进

---

## 九、结论

这次开发流程已经验证出一套有效方法：

- 接力文件保持单入口
- 模块文档拆开维护
- 功能先跑通真实链路
- 每轮都补测试、做验证、同步文档、同步 GitHub
- 链接和交互都按真实用户使用习惯收口

以后只要继续沿着这套流程推进，平台就能在不断扩展功能的同时保持可接力、可验证、可发布。
